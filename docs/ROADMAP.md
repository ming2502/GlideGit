## M2 Log 与精细提交

- [x] M2-1 `log-index` crate：流式首屏加载 + 后台全量索引落盘（SQLite）
  - 30 万提交的合成仓库（M1 Mac，release）：首次建索引 3.7 秒（`git log` 本身 2.8 秒）。有 commit-graph 时首屏 0.3 秒，没有时 2.3 秒。再次打开 0.14 秒，增量更新约 0.4 秒，读一页 100 行不到 1 毫秒，索引文件 40 MiB。
  - 基准：`cargo run --release -p glide-log-index --example bench -- <仓库> [缓存目录]`
  - 遗留：仓库没有 commit-graph 时，第一次打开的首屏要等 git 走完整个历史。M2-10 改为在首次建索引后自动写入 commit-graph，之后再走全量历史就快了。超过约 129 万行时，DOM 滚动高度会超过浏览器上限，已在 M2-3 用缩放滚动条解决。
- [x] M2-2 图布局（lane 分配）及增量更新
  - 每 256 行保存一次 lane 状态（检查点），读一页时从最近的检查点重算，30 万提交仓库上一页 100 行约 0.5 毫秒。
  - 有新提交时，从顶部重算到 lane 状态与旧检查点一致为止，通常只算几百行。颜色按列分配，否则主干颜色会随每个新提交整条改变，检查点也就永远对不上。
  - 再次打开时要扫描全表重建检查点，30 万提交约 0.28 秒（M2-1 时为 0.14 秒）。M2-11 让重新打开时不必等这次扫描：首屏直接从数据库读取（30 万提交约 0.5 毫秒），检查点仍在后台重建。
- [x] M2-3 Canvas 提交图 + 虚拟列表
  - 一块 Canvas 叠在列表可视区上，滚动时只重绘屏幕上的行；跨列的线画成贝塞尔曲线，合并提交画空心节点，颜色按列取自主题调色板（亮色、暗色各 8 色）。
  - 虚拟列表的总高度超过 800 万像素（约 30 万行）时，把滚动条按比例缩放，滚轮仍按正常速度滚动。浏览器预览中用 `?commits=2000000` 验证过 200 万行：End、PageUp 和滚轮都能准确定位。
  - 关闭了列表容器的滚动锚定（`overflow-anchor: none`），否则 Chrome 会在占位块高度变化时自行改动滚动位置。
  - 图列最多画 24 列，更宽的部分被裁掉；IDEA 式「折叠长边」以后再做。
- [x] M2-4 Log 过滤：分支、作者、日期、路径、文本、hash
  - 过滤栏：搜索框（提交信息或 hash，⌘F 聚焦）和「分支」「作者」「日期」「路径」四个下拉；条件之间是「且」的关系。
  - 文本、hash、作者、日期用 SQL 查索引；分支和路径交给 git（`rev-list`、`log -- <路径>`），得到的提交集合再与 SQL 结果取交集。
  - 只按分支过滤时，结果对父提交封闭，图照常绘制；其他条件会让历史出现缺口，只显示列表。
  - 换了过滤条件，会取消上一个条件还在运行的 git 命令。选中的提交在新结果中仍存在时保持选中。
  - 30 万提交：文本、hash、作者过滤 60–90 毫秒，路径约 0.4 秒，分支约 1.1 秒（主要是 `git rev-list`）。分支过滤可以改为在索引里沿父提交遍历来提速；M2-10 实测 gix 遍历与 `git rev-list` 一样快，所以暂不改动。
- [x] M2-5 提交详情：变更文件树 + diff
  - Log 下方是详情面板，与列表之间有可拖动的分隔条，高度会记住。左侧显示标题、正文、作者，提交者与作者不同时也显示提交者；hash 点一下即复制，父提交点一下在 Log 中定位。
  - 变更文件按目录分组，显示类型、重命名前的路径和增删行数，↑↓ 切换文件；右侧显示所选文件的 diff。
  - 后端用 `git log -1` 取提交信息，`git diff-tree -r -z -M --raw --numstat` 取文件和行数，各一次进程调用。合并提交与第一个父提交比较，根提交与空树比较。
  - 在 Log 中快速翻动时，只为停下来的那个提交读取详情（60 毫秒去抖，旧请求结果作废）。
- [x] M2-6 Log 右键菜单：checkout、新建分支或标签、cherry-pick、revert、reset
  - 右键菜单（也可按菜单键或 Shift+F10）：checkout 该提交上的分支、checkout 游离 HEAD（先确认）、新建分支、新建标签（填写说明即为附注标签）、cherry-pick、revert、将当前分支重置到此处、复制 hash。
  - 重置对话框可选 Soft / Mixed / Keep / Hard 四种模式，选 Hard 还要再确认一次。合并提交做 cherry-pick 或 revert 时，以第一个父提交为基准（`-m 1`）。
  - 新增全局横幅：合并、变基、cherry-pick 或 revert 中途停下时显示，带「中止」和「继续」。仍有冲突时「继续」不可用；继续时不打开编辑器，沿用 git 准备好的提交信息。
  - 新分支名、标签名和提交 id 在传给 git 前检查，不能被当作命令行选项。
- [x] M2-7 CodeMirror 6 diff：并排视图、字符级差异、折叠
  - 基于 `@codemirror/merge`：并排（MergeView）和统一（unifiedMergeView）两种布局，选择会记住；字符级差异高亮；未改动的区域折叠成「N unchanged lines」，点击展开；F7 / ⇧F7 在修改之间跳转。
  - 根据文件名按需加载语法高亮（`@codemirror/language-data`），配色取自主题变量，亮色、暗色各一套。CodeMirror 单独打包、首次用到时才加载：主包 296 KB，diff 编辑器 318 KB。
  - 后端新增「读取文件两侧全文」：工作区直接读磁盘，暂存区和提交用 `git cat-file --batch` 流式读取；单侧超过 8 MB 或含 NUL 字节（二进制）时只返回标记。Changes 视图和提交详情都改用这种方式。
  - diff 计算超时 1.5 秒后退回较粗的结果，大文件不会卡住界面。
- [x] M2-8 块级 / 行级 stage 与 discard（`git apply --cached`）
  - 在 Changes 视图的 diff 中，每个修改块有三态勾选框（未暂存 / 部分 / 已暂存），每个增删行有单独的开关。并排布局下删除行和新增行都能按行勾选；统一布局只支持整块勾选。右键勾选框可以暂存、取消暂存，或丢弃此块（先确认）。
  - 实现上没有用 `git apply --cached`。前端按勾选结果算出这个文件在暂存区应有的完整内容（HEAD 加上选中的块和行），后端用 `git hash-object -w --path` 加 `update-index --cacheinfo` 写入，文件模式沿用原条目。这样不会遇到补丁上下文和偏移对不上的问题，CRLF 等换行转换也由 git 自己的 clean 过滤器处理。
  - 勾选状态由三个版本推算：后端随 HEAD↔工作区的 diff 一并返回暂存区内容，前端把它逐块匹配回 diff 的修改块。
  - 丢弃块会直接写回工作区文件，写之前先确认文件在加载 diff 之后没被改过；如果这块已经暂存，会一起取消暂存。
  - 非 UTF-8 文件、含单独 CR 的文件、冲突文件和已删除文件不提供块级操作。
  - 前端加入 vitest（`pnpm test`）并接入 CI：19 个暂存逻辑单测，其中一部分直接使用编辑器自己的 diff 算法生成的修改块。
- [x] M2-9 Stash 列表、应用、弹出、查看 diff
  - 新增 Stash 视图（⌘8）：左侧列出 stash 的说明、所属分支和时间；可以应用、弹出、删除（删除前确认，也可按 Delete），双击即应用，右键也有同样的菜单。可勾选「恢复暂存状态」（`--index`），勾选会被记住。
  - 右侧沿用提交详情面板显示 stash 内容。已跟踪文件与 stash 的第一个父提交比较；未跟踪文件取自第三个父提交，标为「未跟踪」。
  - 「Stash 修改…」（⌘⇧S）：可填写说明，可选择包含未跟踪文件、保留已暂存的修改（`--keep-index`）。后端也支持只 stash 指定路径。
  - 弹出和删除前，先确认 `stash@{n}` 仍指向界面上看到的那个提交；列表在此期间变了就拒绝执行，不会误删。
  - `git stash` 内部用到 `:/` 等特殊路径写法，所以 stash 命令要关闭全局的 `GIT_LITERAL_PATHSPECS`；用户指定的路径改为逐个加 `:(literal)` 前缀，仍按字面匹配。
- [x] M2-10 用 gix 读取热点数据（status、revwalk）；在大仓库上跑基准对比
  - 结论：暂不引入 gix。在 6 万文件、801 个引用的合成仓库和 30 万提交的仓库上（macOS，release）：
    | 操作 | gix 0.90 | git CLI |
    |---|---|---|
    | 读取 801 个引用 | 28 ms | 22–43 ms |
    | status（6 万文件） | 155–228 ms | 150 ms |
    | 遍历 30 万提交 | 251 ms | 254 ms |

    吞吐上没有优势，只省掉了启动进程的开销（macOS 约 15 ms，Windows 通常 30–60 ms）。代价是编译时间多约 80 秒、二进制更大，而且 status 的行为与 git 有差异（fsmonitor、子模块、untracked cache）。
  - 真正的优化方向是减少每次刷新启动的进程数。新增 refs 指纹：只对 refs 目录、packed-refs、reftable、HEAD 和 HEAD reflog 做 `stat`，不启动任何进程；链接工作树会去 common dir 里取 refs。指纹不变时，复用上次的分支列表，Log 索引也跳过更新。每 30 / 60 秒仍会强制读一次，作为兜底。
    - 效果：编辑文件触发的刷新从 4 个 git 进程降到 1 个（只剩 `git status`）。小仓库单次刷新从 34 ms 降到 18 ms，在 Windows 上省得更多。
  - 首次建好索引后，如果仓库还没有 commit-graph，就在后台执行 `git commit-graph write --reachable --changed-paths`。它和 `git gc` / `git maintenance` 写的是同一个缓存文件。之后首屏读取更快（30 万提交：2.3 秒降到 0.3 秒），路径过滤也会用上 Bloom 过滤器。
  - 6 万文件时，status 本身约 150 ms，其中扫描未跟踪文件约占 90 ms。开启 fsmonitor 和 untracked cache 后约 120 ms。这部分是 git 自身的开销，留给 M4 作为可选设置（如开启 fsmonitor），不擅自修改仓库配置。
  - 基准工具：`cargo run --release -p glide-git-backend --example refresh -- <仓库>`，会分项给出 status、refs 指纹和分支列表的耗时。
- [x] M2-11 快照缓存（stale-while-revalidate 启动）
  - 仓库快照：每次变化后写入应用缓存目录（`snapshots/<路径哈希>.json`）。写入合并去抖，先写临时文件再改名，不会留下写了一半的文件。打开仓库时先返回缓存快照（标记 `stale`），状态栏显示「正在刷新…」，`git status` 在后台执行，新快照通过事件替换旧的。
    - 6 万文件的仓库：打开到第一个快照从 355 ms 降到 24–28 ms（剩下的主要是 `Repo::open` 的两次 `rev-parse`），新快照约 255 ms 后到达。
  - Log 索引：每次更新后记录行数和 ref 标签。重新打开、尚未加载完时，状态里直接给出行数，分页按偏移量直接查表。前 2 万行仍按从顶部开始的布局画图，更深的行先不画图，加载完成后版本号递增，页面重新读取。
    - 30 万提交：重新打开后首页 0.5 ms，原来要等约 290 ms 的加载。
  - 多个标签页本来就是并行恢复的，现在每个仓库都能立即拿到缓存快照，不会因为某个大仓库慢而一起等待。
  - 测试覆盖：缓存的读写往返、根路径校验、损坏文件、「先旧后新」的会话流程，以及加载前后分页内容一致（行、标签、图）。
